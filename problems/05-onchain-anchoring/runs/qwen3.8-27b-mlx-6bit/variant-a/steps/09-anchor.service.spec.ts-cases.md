## reply

- `anchorDocument persists the tx identity before broadcast` — with a fake whose `broadcast` throws, the returned proof carries a non-empty `txId` and the row is `broadcasting` with that `txId` set, proving the pre-broadcast persist ordering. Fails if the code persists `txId` after broadcasting, skips the `pending → broadcasting` update, or derives the proof's `txId` without persisting it.
- `anchorDocument broadcast timeout leaves the row in broadcasting limbo (not failed, not confirmed)` — after a rejecting `broadcast`, `anchorDocument` still resolves (no throw) and the row is `state=broadcasting` with a valid `txId`. Fails if the service marks the row `failed` on unknown-outcome timeout, throws to the caller, or rolls back the tx identity.
- `anchorDocument persists the canonical content with a matching hash` — the row's `content` field is the JSON string of the input and its `contentHash` equals `hashContent(input)`; a later `verify` of the same object returns `ok:true`. Fails if the stored content diverges from what was hashed (e.g. raw input stringified differently) so verify would mismatch its own anchor.
- `anchorDocument returns a proof with the correct identity fields` — for a fresh anchor, the returned proof has the request's `documentId`/`version`, the canonical hash of the content, and the `txId` from `prepare`. Fails if fields are swapped, the hash is of the uncanonicalized string, or the `txId` isn't the one `prepare` produced.
- `anchorDocument returns blockNumber 0 for an anchor not yet confirmed` — when no receipt exists after broadcast, the proof's `blockNumber` is the pending sentinel `0`, not a mined block. Fails if the service fabricates a block number, returns null/undefined, or waits for confirmation that never comes.
- `anchorDocument rejects an already-anchored pair with DuplicateAnchorError and does not broadcast` — a second anchor for the same `(documentId, version)` throws `DuplicateAnchorError`, the chain client records no new broadcast, and the row count stays 1. Fails if the service checks-then-inserts instead of relying on the unique index, swallows the duplicate into a success, or re-broadcasts anyway.
- `anchorDocument rejects non-serializable content with CanonicalizationError and persists nothing` — circular-reference content throws `CanonicalizationError` before any insert: the repository has no row and no chain call was made. Fails if hashing happens after the insert, or a partial row is left behind.
- `concurrent anchorDocument calls for one pair yield exactly one row` — two concurrent calls (broadcast serialized so the first insert lands before the second) resolve to one success plus one `DuplicateAnchorError`, and exactly one row exists. Fails if the unique composite index is missing, or a check-then-insert race lets both succeed with two rows.
- `crash between broadcast and late persist loses no anchor: recovery confirms from the chain without a second row` — fake `broadcast` throws (simulating the crash before the naive design's late persist), then `runRecoverySweep` confirms the row with the receipt's block number; exactly one row exists and its `txId` equals what `prepare` deterministically re-derives. Fails if recovery re-inserts a row, if the pre-broadcast `txId` persist is missing (recovery can't find the tx), or if `prepare` isn't deterministic so the re-derived `txId` misses the on-chain receipt.
- `recovery re-broadcasts when the chain has no record of the tx` — for a `broadcasting` row with no receipt, the sweep re-broadcasts the recovered signed payload and counts it resolved, leaving the row `broadcasting` (a successful re-broadcast is not a confirmation). Fails if the sweep confirms on re-broadcast success, marks it failed, or never re-broadcasts an unlanded tx.
- `recovery leaves the row broadcasting when a receipt exists but has no block yet` — for a `broadcasting` row whose receipt is `{found:true, blockNumber:null}`, the sweep changes nothing and counts 0. Fails if it confirms with a null/zero block, marks failed, or re-broadcasts a tx the chain already knows.
- `recovery marks the row failed when re-broadcast rejects and no receipt exists` — with no receipt and a rejecting `broadcast`, the row ends `state=failed` and is not counted resolved. Fails if unknown-outcome re-broadcast failure leaves the row `broadcasting` forever or is counted as resolved.
- `recovery skips a row whose stored txId does not match the re-derived one` — a row whose `contentHash` was tampered so `prepare` re-derives a different `txId` is left untouched (no receipt query against the stored id, no broadcast, no state change) even though a receipt exists for the derived id. Fails if the sweep trusts the stored `txId` over the deterministic re-derivation, or ignores the mismatch and confirms against the wrong tx.
- `recovery is idempotent across passes` — first sweep confirms a `broadcasting` row with a receipt; a second sweep resolves 0 and the row stays `confirmed` with the same block number. Fails if the sweep reprocesses confirmed rows, double-counts, or mutates an already-confirmed anchor.
- `confirmation pass confirms a broadcasting row with the receipt's block number` — `runConfirmationPass` moves a `broadcasting` row with an available receipt to `confirmed` carrying the receipt's `blockNumber`, and returns count 1. Fails if it stores the wrong block, updates `pending`/`confirmed` rows, or miscounts.
- `confirmation pass leaves the row unchanged when no receipt exists yet` — a `broadcasting` row with `found:false` stays `broadcasting` with the same `txId`, count 0. Fails if it marks failed, clears the `txId`, or counts a non-confirmation.
- `confirmation pass skips rows without a txId` — a `broadcasting` row with `txId=null` is not touched and no receipt query is issued. Fails if it queries the chain with a null/empty id or crashes on it.
- `verify returns the proof for matching content` — for a confirmed anchor, `verify` with the same content returns `{ok:true}` whose proof carries the anchor's `txId` and `blockNumber`. Fails if the hash comparison is against the stored raw content instead of the stored hash, or the proof fields come from the wrong source.
- `verify returns a mismatch report (not an error) for different content` — different content yields `{ok:false}` with `expectedHash` = the anchored hash and `providedHash` = the recomputed hash, as a successful result rather than an exception. Fails if mismatch throws, the two hashes are swapped, or the report omits one of them.
- `verify raises ResourceNotFoundError when no anchor exists for the pair` — an unknown `(documentId, version)` throws `ResourceNotFoundError` with no proof and no mutation. Fails if it returns a mismatch against nothing, returns ok, or invents an anchor.
- `verify raises CanonicalizationError on non-serializable content before any lookup` — circular content throws `CanonicalizationError` even though an anchor exists for the pair, and the row is untouched. Fails if the lookup precedes hashing or the error is swallowed into a mismatch report.
- `verify raises ResourceNotFoundError for an anchor that has no txId` — a row with matching hash but `txId=null` (e.g. crashed before the pre-broadcast persist) throws `ResourceNotFoundError` rather than a proof with an empty `txId`. Fails if the proof is emitted with a null/empty `txId`, or a mismatch is reported instead.

Deliberately not testing: canonicalization internals (sorted keys, array order, UTF-8) — owned by `test/canonical.spec.ts`; HTTP status mapping and the error envelope — owned by the controller spec; scheduler/interval behavior, real chain semantics, and exact `signedTx` payload format — out of scope per the plan (interface + fake only).
